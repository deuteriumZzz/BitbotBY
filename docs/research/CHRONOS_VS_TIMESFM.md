# Chronos против TimesFM

Статус на 2026-11-24: **измерен только TimesFM против базисов**; Chronos локально не импортируется (сломан scipy), поэтому прямого сравнения нет. Ablation на торговой ценности не выполнялся — нужны исходы сделок.

## Что установлено
- TimesFM 2.5 (`google/timesfm-2.5-200m-pytorch`): код пакета `timesfm 3.0.2` и веса — Apache-2.0, доступ без токена, веса 925 МБ. Утверждение «TimesFM 3.0 non-commercial» к этим весам не подтвердилось (проверено по карточке модели на Hugging Face).
- Живёт в отдельном окружении `.venv-timesfm` (Python 3.11): бот на Python 3.9, а пакет требует ≥ 3.10. Общение — изолированный воркер (`src/forecast`), JSON по stdin/stdout, нагрузка ограничена `nice` и числом потоков.
- На Mac с Intel `torch` не новее 2.2.2; в нём `scaled_dot_product_attention` возвращает NaN на полностью замаскированных строках. Воркер подменяет NaN нулями (как делают новые torch). Заплатка — снять при смене железа.

## Метод
`src/reliability/forecast_eval.py`: общие точки отсчёта и горизонты для всех моделей, в истории только прошлое (look-ahead исключён), базисы naive / seasonal naive / MA, метрики MAE, RMSE, MASE, pinball, coverage, directional accuracy. Ансамблевые веса — только по validation, test один раз (правило ТЗ).

## Первое измерение (BTC/ETH 15m, 1000 свечей, 40 точек отсчёта)
| Актив / горизонт | MASE naive | MASE TimesFM | покрытие p10–p90 (номинал 0.80) |
|---|---|---|---|
| BTC 2 ч | 2.91 | 3.02 | 0.81 |
| BTC 8 ч | 4.56 | 5.01 | 0.77 |
| ETH 2 ч | 2.58 | 2.62 | 0.80 |
| ETH 8 ч | 4.31 | 5.05 | 0.75 |

Вывод: точечный прогноз не лучше naive; интервалы откалиброваны — вероятная польза в оценке коридора и волатильности, а не направления. Оговорки: ~10 дней истории, перекрывающиеся точки отсчёта, один период рынка.

## Как использовать сейчас
Флаг `FORECASTER=timesfm` заменяет Chronos-поправку в `SignalCombiner` (работает при включённом переключателе Chronos); недоступность воркера → поправка нейтральна. По умолчанию — Chronos.
