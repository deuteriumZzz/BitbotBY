# ADR-001 — Хранилища данных и воспроизведение решений (Phase 4)

Статус: принято (2026-11-23), пересматривается на входе Phase 4b/7. Основа: [MASTER_SPEC_v2.md](MASTER_SPEC_v2.md) §3.4, §12.4, §14; [AUDIT_REPORT.md](AUDIT_REPORT.md).

## Контекст (измерено, а не предположено)

| Факт | Значение |
|---|---|
| Транзакционное состояние | SQLite `data/trades_{paper,live}.db` (119 сделок в paper) + Redis (позиции, настройки, дневная ссылка лимита) |
| Объём рыночных данных | CSV-кэш свечей `data/cache` ≈ 157 МБ |
| Журнал решений | JSONL `data/decision_ledger.jsonl`, ротация 50 МБ × 2 |
| Библиотеки в окружении | `pyarrow 21`, `zstandard 0.25` — **установлены, но не объявлены** в `requirements.txt`/`pyproject.toml`; `polars`, `duckdb`, `clickhouse_connect` — нет |
| Целостность SQLite | `trades_paper.db` не проходит `integrity_check` (WAL-режим); `.recover` вернул 94 из 119 сделок (AUDIT_REPORT §10d) |

## Решение

1. **Позиции, ордера, настройки остаются в SQLite + Redis.** ClickHouse не станет источником истины по позициям (MASTER_SPEC §3).
2. **Воспроизведение решений — на Decision Ledger (JSONL).** Запись `replay_input` хранит входы расчёта комбинатора (ответ AI, сигналы SAC, направления Chronos, снэпшоты, контекст, настройки) и ожидаемый результат; `python -m bitbot.research.replay` повторяет расчёт и сравнивает «бит-в-бит». Отдельная БД для этого не нужна.
3. **Parquet + ZSTD — формат датасетов SAC и архива журнала.** `pyarrow` и `zstandard` уже есть; при первом использовании (Dataset Builder, Phase 7) их нужно **объявить в зависимостях**, а не полагаться на окружение.
4. **ClickHouse — отложен, не отклонён.** Сейчас объёмы (сотни МБ) обслуживаются файлами и SQLite. Возвращаемся к решению, когда выполнится любое условие: (а) WS-ingestion (Phase 4b) пишет тики/стакан и история растёт на ≥ единицы ГБ/нед; (б) запросы по истории в pandas/Parquet перестали укладываться в минуты; (в) нужен многопроцессный доступ к аналитике. Интерфейс чтения датасетов делаем независимым от хранилища, чтобы замена не потребовала переписывать обучение.
5. **Polars — отложен** (pandas достаточно на текущих размерах; без измеренного узкого места новая зависимость не оправдана).
6. **Event sourcing.** Журнал решений — event store *решений* (сигнал → решение → исполнение), рыночные ряды хранятся отдельно (Parquet/файлы). Смешивать их не нужно.

## Что НЕ решено этим ADR (следующие шаги)

- **Бэкап и проверка SQLite.** Нужны `PRAGMA integrity_check` при старте, периодическая копия (`.backup` API, а не копирование файла при активном WAL) и алерт при ошибке. Это трогает базу сделок, поэтому делается отдельным изменением по вашему «go».
- Версионирование датасетов, lineage, retention и point-in-time выборки — в рамках Dataset Builder (Phase 7), когда появится потребитель.
- Хранение полного snapshot входов для AI (в журнале только хэш промпта).

## Последствия и риски

- Replay проверяет детерминированную логику комбинатора; недетерминированные части (LLM, инференс SAC, прогноз) берутся из записи — их качество replay не оценивает.
- Журнал растёт на каждое решение с рекомендациями; ротация ограничивает диск, но не хранит историю дольше нескольких суток — для долгих исследований нужен архив в Parquet.
