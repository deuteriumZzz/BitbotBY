# ADR-002 — Надёжность исполнения (Phase 5)

Статус: принято (2026-11-23). Основа: [MASTER_SPEC_v2.md](MASTER_SPEC_v2.md) §5, [AUDIT_REPORT.md](AUDIT_REPORT.md) (H-7, §10e).

## Что сделано

| Пункт | Решение |
|---|---|
| Ложное «позиций нет» | `fetch_positions` при любой ошибке возвращал `[]`; сверка принимала это за «позиции закрыты» и убирала их из мониторинга. Добавлен `fetch_positions_checked` (ошибка → исключение); стартовая и периодическая сверка используют его. Спот (нет API позиций) пропускается с предупреждением. |
| Периодическая сверка | Каждые `RECONCILE_INTERVAL_S` (60 с), live, не спот. По умолчанию **только обнаруживает и сообщает**: позиции без наблюдения бота, «призраки», расхождение объёма (>2 %) и стороны. Подтверждение двумя проверками подряд; ордер «в полёте» (плейсхолдер) пропускается; кулдаун алерта 30 мин. Исправление — только при `RECONCILE_AUTOFIX=true` (запускает ту же сверку, что при старте). |
| Ордера с неизвестным исходом | Если после 3 попыток причиной была сеть, ордер помечается неизвестным; сверка ищет его по `clientOrderId`, при исполнении — алерт. Ненайденный/неопределённый ордер снимается как `UNRESOLVED`, а не как «ордера нет». |
| Машина состояний ордера | `OrderState`, допустимые переходы, `classify_order`; повторное или запоздавшее событие из финального состояния отбрасывается. Пока используется для классификации найденных ордеров; полноценный поток событий появится с WS (Phase 4b). |
| Идемпотентность | Уже была (`orderLinkId` стабилен между повторами, поиск перед повтором); покрыта тестом «ответ потерян — дубля нет». |
| Reduce-Only | Закрывающие ордера на фьючерсах — `reduceOnly` (багфикс C-9). |

## Что осознанно НЕ делается (и почему)

1. **Dead Man's Switch (Cancel All After) — не подходит этой архитектуре.** Он отменяет *открытые ордера*, а биржевые SL/TP бот ставит именно как защиту на случай собственного падения. Отмена по таймеру сняла бы эту защиту. Возвращаемся к вопросу, если защита позиций перейдёт на условные ордера на стороне позиции (trading-stop), а не отдельные ордера. Параметры API Bybit при этом нужно сверить с актуальной документацией (§14).
2. **In-flight margin** — неприменимо сейчас: вход идёт рыночным ордером, SL/TP — `reduceOnly` и маржу не резервируют. Вернуться при лимитном входе (Post-Only/TWAP).
3. **Smart Execution (TWAP, Post-Only chase)** — только после замера slippage на Paper (MASTER_SPEC §4/5): без данных непонятно, есть ли что экономить. Требует и очереди ордеров/WS.
4. **Partial Fill Manager** — рыночный вход обычно исполняется целиком; ответ `create_order` у Bybit не содержит надёжного `filled`, поэтому подгонять объём позиции под него нельзя без отдельного запроса статуса. Расхождение объёма теперь ловится периодической сверкой (qty-mismatch).
5. **Internal Ledger с funding и net PnL** — funding не учитывается ни в истории сделок, ни в опыте SAC (AUDIT M-10); требует запроса funding по закрытой позиции и изменения учёта PnL — отдельное решение.

## Риски и ограничения

- Периодическая сверка в проде не проверялась на реальной бирже; формат `side`/`contracts` у ccxt для Bybit линейных контрактов предполагается как в стартовой сверке (`contracts`, `side=long|short`).
- Ложные тревоги возможны при ручных действиях на бирже (закрыли/открыли руками): бот сообщит, но ничего не изменит (авто-исправление выключено).
- Спот остаётся без сверки: нужен отдельный механизм по балансам активов.
